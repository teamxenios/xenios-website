### E. 1:1 square canonical media

**Decision note.** E: 1:1 square canonical product media, object-fit contain, identical pixels on card and detail, no grading or crop, safe fallback. Implementation-impact map only. Read-only analysis of Core 8549011 (runtime = 3eaa017).

**Summary.**

Core has three product-media renderers today, and none of them is 1:1.
- MemberCatalogExperience.tsx:116-131 is a 4:3 contain slot. The width={4} height={3} attributes are ratio hints, not the image's real dimensions. With null media it renders no slot at all.
- MemberProductDetailExperience.tsx:165-183 is a 4:3 contain slot. Its no-image fallback (177-182) uses the supplier_pending panel, which shows "Supplier confirmation pending" and "Awaiting documentation" (kit.tsx:69). That gives a false reason for a missing image.
- CatalogDiscoveryPresentation.tsx:52-69 renders at the image's own aspect ratio (height:auto from DTO width/height), so the 800x600 fixture shows 4:3. This component is not routed anywhere.

The public catalog card (EarlyAccessProductCard.tsx:192-204) deliberately has no media slot. No public product detail route exists: /products/:slug goes to ProductUnavailablePage (App.tsx:196).

Data contracts:
- **Public catalog DTO:** carries no media. The storefront unit has only `imageState` (storefront-view.ts:74). It is always "none", because the variant-bound image is listed as an unsourced fact (product-control-source.ts:154-157).
- **Member DTO:** carries href and altText but no width, height or content hash (member-catalog.ts:27-36).
- **CatalogDiscovery DTO:** has width and height but nothing produces it.
- **Product Control:** the AdminProductMedia type and the research_product_media table have no width, height, hash or variant binding (product-admin.ts:151-165; migration 20260726143000:194-219).

E therefore needs:
1. One shared 1:1 contain component in client/src/research/ (allowed write zone, Core lane).
2. Dimensions derived on the server from the uploaded bytes at confirm time. confirmMediaUpload already downloads the bytes and checks the file signature (product-admin-production.ts:811-861). The results go into new nullable columns added by a NEW migration, because the base migration's checksum is pinned (product-admin-integration.test.ts:97-102).
3. Width, height and a content hash threaded through the member DTO, the server projection and the client adapter.
4. A content hash to prove "identical pixels". sourceVersion is a fingerprint of metadata, not of content (member-catalog-service.ts:144-149).

Every file E touches is in an allowed write zone. None is HARD or SEAM unless the implementation reaches for:
- a global CSS class in index.css (HARD);
- a static.ts change for static image delivery (HARD);
- an image-size npm dependency (package.json is HARD);
- an App.tsx route (SEAM);
- a CSP change: care-document-csp.ts is outside every allowed zone, and CSP edits in server/index.ts are forbidden for that seam.

Two sequencing hazards dominate:
- **Media is a commerce input at Core HEAD.** It feeds cart selection, member display state and a persistent-cart SQL join. An active lease (#0, XENIOS-IMAGE-COMMERCE-DECOUPLING-20261001) owns exactly those DTO, server, adapter and admin paths, and its successor branch b38db0a is not merged. Any geometry gate added before that branch lands would hold back or delist products.
- **Probable bucket mismatch.** The member read path signs and validates against 'research-product-media' (member-catalog-service.ts:39; member-catalog-projection.ts:90-91). Uploads go to 'research-product-media-production' (product-admin-production.ts:39-40; migration :930). That would make uploaded images fall back everywhere. This needs verifying.

Imagery lane consequences:
- The calibration lock is already 1:1 at 1254x1254 (manifest :16, :53-144; build-calibration-evidence.mjs:61), so no re-render is needed for geometry. The 4:3 member panel in the preview becomes a historical study.
- A 1:1 canvas in a 1:1 contain slot is never letterboxed or cropped. Framing measured once on the canonical bytes is therefore exactly what renders at every breakpoint, provided width === height is checked first.
- The report-27 framing gate needs restating as fractions of the side S:
  - subject height 0.61-0.75 S, target about 0.68;
  - horizon band 653-721 px, which is 0.521-0.575 S;
  - top margin in the 01/02 reference range of 0.163-0.179 S;
  - centred, with no contact with any edge;
  - a width bound to be added (04 measured 79% wide);
  - the measurement method's absolute-pixel parameters scaled to S.
- Two choices remain:
  - **Canonical bytes:** the 1254 PNG master or the 1024 WebP delivery file named in PRODUCT_IMAGE_STYLE_GUIDE.md:19.
  - **Surfaces:** report 27's fourth correction, "decide which surfaces carry imagery", is still D scope.
- E does not authorize Batch 1 rendering or publication.
