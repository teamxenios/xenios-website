## Actual authority

`supabase/candidates/business_inquiry.sql` is the transaction authority; the concrete Supabase RPC adapter calls it. There is no in-memory production store. Explicit `web` provenance and `b2b_organization` category are stored; no fabricated email envelope is submitted to the existing mailbox bridge.

Submission stores immutable enquiry facts, workflow version 1, a received event and a minimal durable notice intent together. A database-derived SHA-256 fingerprint includes JSONB payload equality and the trusted actor/organization binding. A transaction advisory lock serializes the owner/attempt pair. An equal retry returns the original reference; changed content conflicts. Exact replay precedes new-intake feature/policy readiness checks. Organization-bound retries still recheck membership. The opaque owner binding must be resolved by Root from a secure server context, never a public body or contact address.

Payloads retain exact requested presentation, quantity **and its unit**, packaging preference, site count, replenishment, services and bounded contextual fields. Selections may be empty for an exploratory enquiry. Quantities express demand, not validated supplier availability, a quote or an accepted order. No supplier MOQ/increment, private cost, aggregate mixed-unit total, procurement or payment behavior is inferred. Referral text is unverified attribution and grants no access or ownership.

List/detail calls verify actual confirmed, unbanned Auth identity, enabled business-specific Care capability and live business-specific Care role in SQL, then record the actual read. Existing Early Access readers do not inherit business access. Assignment requires the separate operator capability/role; it locks the workflow row and compares the expected revision. An immutable command result makes a retry safe even after a newer assignment. Changed command reuse or competing stale revisions conflict. Owners must themselves be eligible operators; no referral or matching email appoints an owner.

Organization reads and submissions recheck the **existing** canonical B2B relationship/operator/member binding, with owner/admin/business-buyer roles matching the existing organization claim boundary. A billing-viewer-only role does not grant enquiry access. Arbitrary organization selectors, email domains and referral strings cannot establish membership. Missing canonical tables fail closed. The organization list returns only that relationship's enquiries; anonymous enquiries are not retroactively attached by contact email. No named-buyer entitlement/pricing profile is copied to the general business path.

Private tables have RLS and no browser ACLs. Public RPCs are `SECURITY INVOKER`, with empty search paths and execute restricted to the trusted service role. The private schema is not a browser API. Service-role callers are trusted server infrastructure; a stolen service secret is outside the browser permission boundary. Configuration values are read-only to the server. PostgreSQL row locking requires UPDATE on at least one column, so only the constrained true-only `singleton` key has a column UPDATE grant; the server cannot change activation, readiness or policy fields. Facts/events/command history cannot be updated/deleted through service-role grants. The server may update the workflow. No credentials or customer fields are logged by the new adapter/routes.
