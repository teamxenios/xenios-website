## First, set the right Quick Order milestone

The current repository still has an **unmounted, disabled Quick Order implementation**. The interface, validation and HTTP safety work exist, but durable submission and actual operator readback are not implemented. The route/privacy patch is prepared, not applied. This is more than a final test or a switch to turn on. 

The existing persistence proposal also identifies a real backend gap: the current submission function cannot atomically preserve the new referral/affiliation information and enforce the required currentness rules. Adding another write afterward would risk partial requests. 

Therefore, I recommend three distinct milestones:

| Milestone | What the customer can actually do | Required outcome |
|---|---|---|
| **A. Quick Order intake** | Select eligible products, enter their details, submit a request and receive a reference. | The request is durably saved once, recoverable after a lost response, and visible to an authorized operator. |
| **B. Quick Order purchasing** | Accept an eligible quote and pay through the approved payment method. | Payment is independently verified against the correct request, amount and currency before fulfillment can advance. |
| **C. Full-site completion** | Use the complete catalog, account, partner, subscription, status and support journeys. | The included features are integrated, independently reviewed, qualified and verified in production. |

**A one-hour checkpoint is useful. A promise that customers can buy in one hour is not supported by the current implementation.** If taking payment must be part of the first live release, that release must meet milestone B as well. We should not quietly launch request intake and call it checkout.

The first-hour target should be **demonstrable source progress, executed tests where permitted, and a precise remaining path to live intake**. The production milestone follows when the actual customer journey works.

## How to run the sessions

My proposed starting configuration is **one coordinator, the existing Quick Order owner, the original acceptance reviewer, and only the necessary independent specialists**. Initially, cap local source writing at two concurrent owners and heavy local execution at one job.

That approach matters because worktrees separate file changes but still run on the computer or remote environment containing the project. They do not provide additional physical RAM. Anthropic also notes that agent teams add overhead and work best on independent tasks; same-file or heavily dependent work often benefits from fewer sessions. [OpenAI Developers](https://developers.openai.com/codex/app/worktrees)

Your larger subscriptions help with model usage, but **they are not unlimited execution or additional laptop memory**. Check the actual allowance and runner before scaling up, and do not silently switch to paid overages. [OpenAI Help Center](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)

The coordinator should reuse parked owners where suitable. A new session requires a concrete task, a non-overlapping file assignment and available resources. **No new harness version is required to start this work.**
