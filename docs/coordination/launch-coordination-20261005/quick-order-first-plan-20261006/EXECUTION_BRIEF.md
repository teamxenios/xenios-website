# Xenios full-site completion brief | Quick Order first

## Objective and audience

Complete the existing website for customers, gym/partner referrals and internal
operators. Quick Order is the first business milestone; full purchasing and the
rest of the website follow. Use existing canonical systems and the reviewed
premium UI, not a new storefront or tool stack.

The user requested roughly twelve code-work packages and the labels Supreme,
Mega, Gold and Bronze. This plan interprets those as twelve distinct work
packages grouped three per label. They are not four provider subscription plans,
model classes or levels of acceptable quality. All request the strongest stated
runtime actually available. A work package can be a bounded subtask in an
existing session; it does not require another desktop window.

## What is already decided

- Quick Order target is /health/quick-order and its existing API namespace.
- The implemented contract is request intake, not payment or clinical approval.
- Reuse canonical catalog, Auth, order ledger, outbox and operator workflow.
- Existing A-E/S1-S7 visual reference: Health header/footer, native shell,
  rectangular black customer actions, restrained focus accents, square media.
- Trusted attribution differs from what a customer types about a referral.
- Existing source acceptance, holds and evidence must be preserved.
- The bridge harness is supporting tooling and is OFF this critical path.

## Missing items that materially change the result

Must decide or authorize before the dependent action:
- exact held mount/PWA source scopes and persistence/currentness expansion;
- approved Health legal, product/destination and standing authorities;
- an approved usable independent payment rail before live buying;
- current Core-hash/GATE-01 disposition and exact managed/release action;
- actual runner/workspace/account authority for consequential execution.

Helpful but not needed to block unrelated source work:
- final nonessential image library and optional animation/polish;
- future harness automation after a separately approved pilot;
- subscription enhancements beyond the selected launch offer.

Safe engineering assumptions within existing scope:
- reuse current UI and canonical data rather than redesign;
- use truthful image fallbacks;
- keep unknown offers/provider/payment capabilities unavailable;
- prefer a single independently reviewed customer slice over a broad merge;
- use synthetic nonproduction identities during qualification.

## Recommended product sequence

Release A: durable Quick Order request intake and operator readback.
Release B: independently verified purchasing through the selected payment rail.
Release C: full-site completion, including approved media, partner reporting,
recurring product flow and remaining customer/admin journeys.

This staging is a recommendation, not a claim Samuel already approved a
request-only launch. If the first live release must accept money, it must meet
Release B's requirements before it is customer-ready. Do not silently ship
request-only and label it buying.

## Execution tempo

Use a four-hour planning/work window with a factual checkpoint at 60 minutes.
There is no evidence-based guarantee of a live one-hour checkout: canonical
persistence and decisive authorities are still missing. The first hour should
produce executable deltas/tests and a clear remaining path, not a claimed
production date. Continue ready source work while specific dependencies wait.

Protect the time budget: no new harness versions, new task system, gratuitous
record rewrites, repeated completed audits, broad redesign or uncontrolled
parallel local builds. Twelve packages are a backlog/ownership map, not twelve
unbounded agents.

## Success

Show an exact candidate performing the selected business journey through real
approved adapters and durable storage, then independently qualify and deploy it
through the actual release process. Source acceptance, tests and deployment
remain distinguishable outcomes. No fabricated percentage complete.
